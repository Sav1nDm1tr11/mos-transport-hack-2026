# Техническое задание: система прогнозирования задержек наземного транспорта

Версия: 1.0. Дата: 25.09.2026. Статус: проект ТЗ для согласования и последующей разработки.

Документ определяет первую полностью работоспособную версию: от приёма телеметрии и подготовки модели до рабочего места оператора, истории ситуаций и формирования конкурсного результата. Это требования к будущей реализации, а не заявление о готовности существующей системы.

Требования разделены по происхождению:

### 1.2. Цель продукта

Оператор должен своевременно обнаружить ожидаемое отклонение от расписания, понять место, целевое время, основания и ограничения прогноза, подготовить сведения для решения во внешнем рабочем процессе и затем проследить изменение ситуации.

Основная единица работы — ситуация, требующая внимания, связанная с конкретным ТС и плановым посещением. Каждый пересчёт модели обновляет данные ситуации, но не создаёт отдельное предупреждение.

Полезный результат первой версии — замкнутый цикл:

`телеметрия → плановый контекст → прогноз → предупреждение → анализ оператором → сводка → повторное наблюдение → история`.

### 1.3. Границы ответственности

Сервис информирует и помогает анализировать. Он не передаёт команды водителям, не выпускает резерв, не согласует объезд и не управляет светофорами. Просмотр предупреждения не означает выполнение действия. Снижение прогнозируемой задержки не доказывает предотвращение нарушения.

Система предназначена для одного оператора сети/перевозчика с несколькими пользователями. Мультитенантная SaaS-платформа, платёжные функции, пассажирское приложение и кабинеты водителей в первую версию не входят.

### 1.4. Выбор архитектурного подхода

| Подход | Преимущества | Ограничения | Решение |
|---|---|---|---|
| Единый процесс с PostgreSQL | Минимум инфраструктуры | Приём, вычисления и UI конкурируют; сложнее изолировать ML и воспроизводить поток | Не выбран для целевого контура |
| Отдельные gateway, worker, ML и backend; Kafka, PostgreSQL, Redis | Соответствует исходной архитектуре, изолирует ответственность, позволяет повторное чтение | Требует настройки нескольких сервисов | **Основной вариант** |
| Распределённая обработка с Flink/Spark, отдельной аналитической БД и кластерным инференсом | Возможность дальнейшего масштабирования | Дополнительные эксплуатационные затраты без подтверждённой потребности | После измерений |

В первой версии работает один `processing-worker`, внутри которого разделены обработка телеметрии, сопоставление с планом, планировщик прогнозов и правила ситуаций. Независимое масштабирование этих модулей не требуется для первой приёмки.

## 4. Термины и неизменяемые правила предметной области

| Термин | Определение |
|---|---|
| ТС / `tr_id` | Транспортное средство, ключ связи телеметрии и плана |
| Устройство / `unit_id` | Бортовой терминал; связь с ТС хранится отдельно |
| Плановое посещение / `stop_visit_id` | Конкретное прибытие по расписанию: `tt_action_item_id` в CSV |
| `target_stop_id` | Имя того же ID посещения в конкурсных точках и ML API; не ID физической остановки |
| Физическая остановка | Отдельный объект справочника, который нельзя автоматически отождествлять с посещением |
| `T` / `as_of` | Момент, на который фиксируется входной срез прогноза |
| `delay_s` | Фактическое прибытие минус плановое, в секундах со знаком |
| `cur_dev_s` | Отклонение на последней обнаруженной пройденной остановке, а не точная задержка между остановками |
| Прогноз | Неизменяемый результат для ТС, целевого посещения и `as_of` |
| Ситуация | История предупреждения для ТС и конкретного посещения, обновляемая сопоставимыми прогнозами |

Правила P0:

1. Онлайн-цель — первое по плановому времени посещение данного ТС в окне `(T + 10 минут, T + 15 минут]`. Левая граница исключается, правая включается.
2. При одинаковом минимальном времени у разных посещений цель признаётся неоднозначной, пока импорт не устранит конфликт. Произвольный выбор по ID запрещён.
3. В офлайн-точках цель уже задана: использовать `target_stop_id` и `target_time_begin`, проверяя их согласованность с планом, без замены другой целью.
4. При отсутствии онлайн-цели возвращать причину `no_target_in_window`; не использовать более близкую остановку или другой горизонт.
5. Прогнозное время прибытия = плановое время + `delay_s`. Знак сохраняется во всех API, графиках и экспорте.
6. До планового прибытия +10–15 минут не означает столько же времени на вмешательство или до начала нарушения.
7. Прогноз не становится наблюдаемым фактом после наступления планового времени. При отсутствии надёжного факта исход остаётся неизвестным.
8. Отсутствие данных — `null` и код причины. Ноль означает реальное числовое значение.
9. При смене цели начинается другая серия прогнозов. Дельту задержки между разными целями нельзя подписывать как улучшение или ухудшение одной оценки.

### 5.2. Импорт и качество — F01

Импорт выполняется воспроизводимой CLI-командой или административной задачей; отдельный сложный экран загрузки не обязателен. Результат: версия набора данных, контрольные суммы файлов, число принятых/отклонённых строк и отчёт с причинами.

Обязательные проверки:

- Наличие колонок, UTF-8, разделитель, типы; ID читать строками, включая отрицательный `packet_id`.
- Уникальность посещений в версии расписания; повторная загрузка не создаёт дубликатов.
- Согласованность `tr_id`, цели и планового времени; конфликты изолируются, а не исправляются молча.
- Диапазоны широты/долготы, конечность чисел, отсутствие отрицательной скорости. Невалидная позиция не отменяет факт получения пакета.
- Пустые значения сохраняются отсутствующими; `location_valid=False` запрещает использовать координаты как достоверные.
- Связи `unit_id → tr_id` имеют интервал действия. Если одному устройству соответствуют несколько ТС в пересекающееся время, требуется исправление справочника.
- Расписание загружается атомарно: сначала проверка, затем публикация версии; активная версия не меняется посередине среза прогноза.

### 5.3. Время и защита от утечки

Внутреннее время — UTC; API использует ISO 8601 с часовым поясом. Интерфейс по умолчанию отображает `Europe/Moscow`, с явной подписью. Импорт CSV без зоны требует параметра `source_timezone`; угадывать его по местоположению проекта запрещено. Пока параметр не задан, импорт временных данных не запускается. Подтверждение часового пояса — входное условие достоверного запуска, а не недостающая ветка реализации.

Для офлайн-конкурсного расчёта использовать телеметрию с `event_time ≤ T` и данную в точке подсказку `cur_dev_s`. Фактические будущие посещения и `target_delay_s` не попадают в признаки. Для честного онлайн/replay-среза дополнительно учитывать доступность: `receive_time ≤ as_of` и событие уже надёжно обработано к моменту фиксации среза. Сохранять watermark обработки и точный состав входа; одного SQL-фильтра по времени недостаточно для воспроизводимости.

Офлайн-режим по правилам конкурса и replay с задержкой доставки должны иметь разные обозначения в отчётах. Более позднее получение события не меняет ранее опубликованный прогноз.

### 5.4. Демонстрационные данные

Каждый запуск имеет `run_id`, `mode=live|replay|scenario` и версию данных. Все события, прогнозы, ситуации и снимки привязаны к запуску. Данные разных режимов не смешиваются в карте, кеше и метриках.

Replay использует виртуальные часы, исходное плановое время и управляемую скорость. При наличии корректного `receive_time` порядок доступности задаётся им; иначе используется `event_time` и фиксируется допущение нулевой задержки доставки. Пауза останавливает виртуальное старение данных. Системные health-check и тайм-ауты HTTP используют реальные часы.

Сценарные данные допускаются для проверки UX и ошибок, имеют постоянную плашку и не учитываются в MAE. Автогенерация NDTP проверяет протокол и соединения: она не воспроизводит фактические рейсы и не доказывает качество модели.

## 6. Функциональные требования к потоку и прогнозу

### 6.1. Приём NDTP — F02

`telemetry-gateway` слушает настраиваемый TCP-порт, исходно `9201`. Принимает handshake и realtime-пакеты в формате поставленного эмулятора. REST API эмулятора на `18080` не является входным API нашей системы.

Приёмник обязан:

1. Собирать кадры из произвольных TCP-фрагментов и разбирать несколько кадров из одного чтения.
2. Проверять NPL-сигнатуру, допустимую длину, NPH и границы ячеек до чтения полей. Установить предел буфера соединения и тайм-аут неполного кадра.
3. Проверять CRC-16/Modbus по NPH и телу с перестановкой байтов в поле NPL согласно спецификации эмулятора, включая его описанное поведение при нулевых flags.
4. Разбирать навигационную ячейку, масштаб координат `1e7`, знак из битов N/S и E/W, Unix-время и единицы скорости.
5. Поддерживать размеры известных дополнительных ячеек, необходимых для пакета по умолчанию эмулятора. Неизвестную ячейку без известной длины нельзя «пропустить» сканированием: весь кадр изолируется с причиной `unsupported_cell_type`.
6. Сопоставлять устройство с ТС по справочнику на время события. Неизвестное устройство или конфликт handshake/NPL не порождает выдуманное ТС.
7. Публиковать нормализованное событие или запись ошибки; сбой одного устройства не блокирует остальные соединения.
8. Ограничивать очередь публикации. При недоступной Kafka применять backpressure, метрики и контролируемое закрытие соединения вместо бесконечного потребления памяти.

Подтверждения и повторная доставка до Kafka зависят от протокола источника. Поставленный эмулятор не проверяет содержимое ответов сервера; его работа не подтверждает совместимость с реальными терминалами. Гарантия повторной обработки начинается после подтверждённой записи в Kafka. Для подключения реальных терминалов нужен отдельный тест handshake/ACK и поведения при потере связи.

### 6.2. Состояние и свежесть — F03

Worker хранит отдельно последнее полученное сообщение и последнюю пригодную позицию. Более новое сообщение с невалидными координатами обновляет состояние связи, но не переносит маркер в `(0,0)` и не освежает старую координату.

Стартовые пороги относительно часов текущего режима:

| Возраст последней пригодной позиции | Состояние положения | Поведение |
|---|---|---|
| 0–60 с включительно | `fresh` | Обычное отображение; прогноз допустим при выполнении требований модели |
| Более 60 до 180 с включительно | `limited` | Метка ограниченности; новые модельные прогнозы P0 не формировать |
| Более 180 с | `stale` | Старый маркер выделен; отдельная проблема данных |
| Пригодной позиции не было | `unavailable` | ТС есть в списке, маркера нет |

Возраст пакета показывается дополнительно. Наличие свежих пакетов без координат обозначается как «связь есть, позиция недоступна». Время события более чем на 30 с впереди часов приёмника изолируется с `future_timestamp`; порог настраивается. Позднее событие сохраняется в историю, но не заменяет последнюю позицию событием с меньшим `event_time`.

### 6.3. Сопоставление с расписанием — F04

P0 не требует полноценного дорожного map matching. Выбор будущего посещения выполняется по ТС и времени. Для получения `cur_dev_s` применяется отдельная консервативная оценка прохождения плановых точек.

Начальное правило оценки: последовательное продвижение по посещениям ТС; кандидат в пределах ±15 минут от плана; два пригодных наблюдения внутри радиуса 50 м с интервалом не более 30 с. За оценку прибытия принимается первое из этих наблюдений. Эти параметры — допущения для пилота, подлежащие калибровке на train/test.

При нескольких подходящих посещениях, конфликте порядка или пропуске наблюдений оценка не создаётся. Одно посещение не засчитывается повторно. Ближайшая по расстоянию остановка сама по себе не определяет факт прибытия. Повторные посещения одинаковой точки различаются по ID и плановому контексту.

Для оценки сохраняются `arrival_estimate`, `source=stop_matching`, использованные события, версия алгоритма и качество. Это **оценка по GPS**, не подтверждённый факт перевозчика. В онлайн-ML передаются `cur_dev_s`, `cur_dev_observed_at`, `cur_dev_source`, `cur_dev_quality`. При отсутствии однозначной оценки — `null`. Модель P0 должна поддерживать отсутствие `cur_dev_s`; поставка, требующая всегда известного значения, недостаточна для автономного онлайн-контура.

### 6.4. Расчёт прогнозов — F05

Базовый цикл — 30 с, допускается настройка до 60 с. В начале цикла фиксируются `as_of`, версия плана, конфигурации и доступного состояния. Формируются цели и входные срезы. Отсутствие цели, позиции или обязательной истории сохраняется как причина отсутствия прогноза, а не как задержка 0.

Начальный профиль модели: история до 30 минут, не менее трёх пригодных точек за последние 5 минут, последняя не старше 60 с; `cur_dev_s` необязателен. Иные требования допустимы только через версию `model-info` и повторную интеграционную проверку. Хранилище удерживает историю модели плюс 10 минут запаса.

Сохраняются все результаты, включая ошибки по отдельным целям. Только успешный конечный числовой прогноз может участвовать в оценке задержки. Старый ответ не заменяет более новый: сравниваются `as_of` и целевое посещение. История опубликованных прогнозов неизменяема.

Прогноз считается актуальным не более 90 с от `as_of` при свежей позиции и совпадении текущей цели. По истечении срока он остаётся в истории с меткой устаревания; исключается из актуальной тепловой агрегации. Модельные и резервные прогнозы визуально различаются.

### 6.5. Резервный режим

При недоступности ML разрешён `delay_s=cur_dev_s`, только если последняя пригодная позиция свежая, оценка `cur_dev_s` однозначна, её возраст не более 5 минут и целевое посещение выбрано корректно. Результат получает `prediction_mode=fallback`, версию резервного алгоритма и причину. Вероятность не присваивается.

Если условия не выполнены, показывать «прогноз недоступен», сохраняя последнюю историческую оценку. Резервные результаты видны в отдельном слое/фильтре и не открывают новые ML-предупреждения о транспортном риске. Активная ситуация при этом получает состояние деградации данных, а не автоматически закрывается.

### 6.6. Офлайн ML и submission — F06

Поставка включает воспроизводимые команды подготовки признаков, обучения, оценки и формирования submission. Предобработка обучения и инференса находится в одном версионируемом пакете. Выбор алгоритма принадлежит ML-команде; нейросеть или GNN не являются обязательным условием.

Проверки качества:

- Сравнить модель с `prediction=0` и `prediction=cur_dev_s` по MAE в секундах на одинаковом наборе точек.
- До обучения проверить пересечения train/test/validate по ID точек, ТС, времени и повторяющимся событиям. Совпадение первых просмотренных строк traffic не доказывает утечку, но требует полного аудита; не считать названия папок гарантией независимости.
- При пересечениях использовать отдельный временной/group holdout без пересечения целевых посещений, задокументировать схему. Не подбирать параметры по скрытым ответам validate.
- Отдельно показать MAE для опозданий, опережений, недостаточной истории и реальных/синтетических данных, если происхождение можно надёжно определить. Не выдумывать признак синтетичности.
- На одинаковом срезе офлайн и сервисный прогноз должны совпадать с допуском не более 0,001 с для детерминированного CPU-профиля; для иной арифметики допуск документируется до проверки.
- Минимальная продуктовая цель: MAE обученной модели ниже обоих baseline на согласованном holdout. Это критерий приёмки, а не обещание заранее известного результата. При невыполнении платформа может быть технически исправной, но прогнозная часть P0 не принята.

Файл `submission.csv`: UTF-8, разделитель `;`, ровно колонки `sample_id;prediction`, каждый `sample_id` из validate/points один раз, без лишних ID, пропусков, NaN и бесконечностей. Для офлайн-точек с отказом модели используется предоставленный `cur_dev_s`, а число таких случаев входит в отчёт; это отдельное правило полного конкурсного покрытия, не расширение онлайн-fallback. Если и `cur_dev_s` невалиден, сборка submission завершается ошибкой валидации.

Отчёт хранит версии кода/модели/признаков, параметры, seed, контрольные суммы входов, MAE и долю fallback. Локальный MAE validate не вычисляется: эталон скрыт. Упомянутый в README score ≈0,40 — характеристика исходного baseline, не измерение нашей модели.

## 7. Рабочее место оператора

### 7.1. Общая компоновка — F07

Основной экран содержит верхнюю сводку, очередь внимания, связанную карту и открываемую карточку ситуации. Основной рабочий сценарий должен проходить без переходов между несвязанными страницами.

Постоянно видны: выбранная зона, режим данных, время системы/воспроизведения, время последнего обновления и состояние соединения. Доступны поиск по ID ТС/посещения, фильтры риска, качества данных, статуса просмотра и наблюдения. Фильтр маршрута появляется только при наличии проверенного справочника.

Сводка показывает:

- Число новых активных рисков и значимых ухудшений.
- Число ситуаций на личном наблюдении.
- Число ТС с ограниченными, устаревшими или отсутствующими координатами.
- Покрытие прогнозом: число актуальных модельных прогнозов / число ТС с однозначной целью в окне; отдельно — fallback и причины отсутствия.
- Число ТС без цели в окне и общий размер выбранной зоны.

При нулевом знаменателе показывать «нет целей в текущем окне», а не 100% покрытия. Счётчики и список используют один `snapshot_id` и одинаковые фильтры. MAE и технические метрики доступны в отчёте инженера, не занимают центральную часть операторского обзора.

### 7.2. Очередь внимания — F08

Каждая строка содержит приоритет, причину приоритета, ТС, известное название линии либо ID ТС, адрес/ID посещения, плановое время, прогноз отклонения со знаком, время расчёта, свежесть позиции, качество, отметку просмотра и наблюдения.

Отдельные представления: «Риски движения» и «Проблемы данных». Отсутствие телеметрии не превращается в низкий транспортный риск. Основная сортировка рисков: класс приоритета, ближайшее плановое время, модуль отклонения, стабильный ID как последний критерий. Устаревшие оценки сохраняются в соответствующем фильтре и не конкурируют с актуальными как достоверные прогнозы.

Открытая карточка и фокус не сбрасываются при обновлении. Пересортировка списка откладывается, пока пользователь взаимодействует со строкой; показывается индикатор новых изменений с возможностью применить их. Новое критическое событие заметно отдельным уведомлением. Обновления не должны перемещать элемент в момент клика.

### 7.3. Карта — F09

Обязательные слои: последняя пригодная позиция ТС, целевые плановые точки, прогнозное отклонение на этих точках. Выбор строки выделяет ТС и цель; выбор маркера открывает связанную карточку. Позиция обновляется по обработанной телеметрии независимо от цикла ML. Анимация не экстраполирует неизвестное движение.

Карта рисков показывает прогноз обслуживания остановок, а не автомобильные пробки. Правила P0:

- При наличии проверенного ID физической остановки и направления агрегировать по ним.
- Без справочника агрегировать по географическим ячейкам 100 м в локальной метрической проекции, явно подписывая «область плановых точек, направления не разделены». Масштаб карты не меняет саму единицу агрегации.
- Для основной агрегации использовать актуальные успешные модельные прогнозы. Цвет — максимальное положительное отклонение в группе, подпись — число прогнозов выше 120 с / общее число доступных прогнозов. При отсутствии положительных значений максимум опоздания равен 0, но знак отдельных прогнозов сохраняется в деталях.
- Опережения показывать отдельным режимом с собственной легендой; резервные оценки — отдельным слоем. Время и вероятность не смешивать в одной шкале.
- Группы без прогноза обозначать серым/штриховкой; отличать их от групп с допустимым отклонением. При раскрытии перечислять все входящие посещения и исключённые оценки с причинами.
- Качество и риск кодировать цветом, текстом и значком. Для ТС с устаревшей позицией показывать её возраст.
- Не рисовать неподтверждённую трассу маршрута. Линия между точками допустима только как явно подписанная условная последовательность.

Источник картографической подложки задаётся конфигурацией. При его недоступности очередь и карточки продолжают работать, на карте видна ошибка. Для автономной демонстрации нужен разрешённый локальный источник подложки либо явно обозначенная схема координат без подложки; автоматическая загрузка внешних тайлов не является обязательной зависимостью расчётов.

### 7.4. Карточка ситуации — F10

Карточка состоит из пяти блоков:

1. **Ожидание:** ТС, целевое посещение, плановое время, прогнозное время, отклонение, горизонт до плана, время расчёта, модель/резерв.
2. **Наблюдения:** последняя позиция и скорость, возраст пакета и позиции, `cur_dev_s` с источником и временем, качество сопоставления.
3. **Основания:** наблюдаемые паттерны, переданные моделью факторы при их наличии, ограничения и недостающие данные. Правило низкой скорости не называется доказанной причиной задержки.
4. **История:** временной график прогнозов одной цели, плановая отметка, события просмотра/наблюдения и доступная оценка/факт прибытия. Другая цель отображается отдельной серией.
5. **Следующий шаг:** подходящие подсказки, просмотр, наблюдение, копирование, сообщение об ошибке.

Вероятность показывать только при поддержке модели, вместе с определением события, например `P(delay_s > 120)`. Отсутствие вероятности не скрывает точечный прогноз. Оценка качества GPS и вероятность задержки не объединяются в «процент уверенности».

Для внешнего факта прибытия и оценки по GPS используются разные подписи. Если исход неизвестен, это прямо указано; отсутствие факта не заменяется прогнозом или временем архивирования.

### 7.5. Аналитические действия — F11

| Действие | Требуемое поведение |
|---|---|
| Открыть карточку | Показать данные; не подтверждать автоматически просмотр и не менять транспортное состояние |
| Отметить просмотренным | Записать пользователя, время и просмотренную ревизию ситуации; повтор безопасен |
| Поставить на наблюдение | Добавить в личный список до ручного снятия; после архивирования доступно в истории |
| Снять с наблюдения | Удалить из личного списка без удаления ситуации и истории |
| Скопировать сводку | Сформировать текст с временем, целью, прогнозом, качеством, основанием и ссылкой на карточку; выполнить копирование только по действию пользователя |
| Сообщить об ошибке | Тип: данные / сопоставление / прогноз / объяснение; необязательный комментарий; сохранить автора, время, ревизию |

Просмотр и наблюдение персональны. Один оператор не снимает новизну предупреждения для другого. Обратная связь не изменяет модель и исходные факты автоматически; она доступна для последующего разбора. Комментарии отображаются как текст, не как исполняемый HTML.

### 7.6. Подсказки и сводка — F12

P0 использует версионируемые детерминированные правила, без обязательной LLM. Каждая подсказка имеет код, текст, основание, необходимые условия, недостающие сведения и время формирования.

| Условие | Подсказка | Ограничение |
|---|---|---|
| Значимый актуальный риск | Проверить обстановку по доступному внешнему каналу; указать ТС, место и цель | Канал не открывается и сообщение не отправляется автоматически |
| Скорость ≤3 км/ч не менее 90 с при промежутках пригодной телеметрии ≤30 с | Проверить длительную малую подвижность ТС | Не утверждать ДТП, пробку или посадку пассажиров |
| Ограниченная/устаревшая позиция | Проверить качество телеметрии и актуальность последней оценки | Не трактовать пропажу связи как стоянку |
| Активная ситуация на наблюдении | Сравнить следующий прогноз той же цели | Смена цели требует отдельного сравнения |
| Конфликт расписания или привязки | Проверить справочник/план | Не предлагать управленческое вмешательство на ненадёжной основе |

Выпуск резерва, выдержка, объезд и другие изменения движения не предлагаются как готовые P0-рекомендации без данных об условиях их применимости. Прогнозируемый эффект таких действий не рассчитывается.

Сводка активных рисков доступна на экране и в UTF-8 CSV/текстовом экспорте с действующими фильтрами и правами. Содержит момент снимка, режим, зону, ТС, цель, план, оценку, качество, источник, подсказку и статус наблюдения. Формирование сводки не отправляет сообщения и не передаёт ответственность за смену. CSV-экспорт экранирует пользовательские текстовые значения, которые табличные редакторы могут интерпретировать как формулы.

### 7.7. Состояния интерфейса

Для каждого экрана реализовать загрузку, пустой результат, отсутствие прав, частичную доступность, ошибку и повторную попытку. Различать «в зоне нет ТС», «нет рисков», «нет целей», «нет прогноза» и «потеряно соединение».

После обрыва обновлений показывать предупреждение и возраст данных. Сохранённые данные доступны для просмотра, но не выглядят актуальными. Повторная отправка пользовательского действия после сетевой ошибки не должна создавать дубликат записи.

Основной профиль — настольный браузер с разрешением от 1366×768; адаптация к 1920×1080 обязательна. Доступ к функциям через клавиатуру, видимый фокус, текстовые подписи рисков и понятные единицы измерения обязательны. Полноценное мобильное рабочее место — вне P0.

## 8. Правила предупреждений и жизненный цикл

### 8.1. Состояния разделены

Вместо одного неоднозначного `status` сохраняются независимые поля:

- `risk_kind`: `late|early`; `severity`: `attention|critical`.
- `lifecycle`: `active|archived`; причина архивирования обязательна.
- `assessment_state`: `predicted_risk|risk_reduced|outcome_unknown|arrival_estimated|arrival_confirmed`.
- `data_quality`: `fresh|limited|stale|unavailable`.
- Персональные `seen_revision`, `watching`, `last_seen_at`.

`arrival_confirmed` допускается только при наличии внешнего подтверждённого факта. Оценка по GPS даёт `arrival_estimated`. Архивирование не означает восстановление движения или успех вмешательства.

### 8.2. Начальные пороги

Это настраиваемые продуктовые допущения, а не нормативы Москвы. Значения −60/+120 с согласуются со справочными классами датасета; дополнительные пороги введены для устойчивого UX.

| Условие | Действие |
|---|---|
| `delay_s > 120` в двух последовательных пригодных циклах одной цели | Открыть `late / attention` |
| `delay_s > 300` в одном пригодном цикле | Открыть или повысить до `late / critical` немедленно |
| `delay_s < -60` в двух последовательных пригодных циклах одной цели | Открыть `early / attention` |
| Для late: `delay_s ≤ 90` в трёх последовательных пригодных циклах | Архивировать с причиной `risk_reduced`, без заявления о факте восстановления |
| Для early: `delay_s ≥ -30` в трёх последовательных пригодных циклах | Аналогично архивировать `risk_reduced` |
| Critical позднее имеет `delay_s ≤ 240` в трёх пригодных циклах | Понизить до attention; затем применять отдельное правило архивирования |
| Рост задержки ≥60 с относительно последнего уведомления той же late-ситуации или повышение до critical | Создать уведомление об ухудшении; обычный cooldown 120 с, повышение до critical обходит его |

Пригодный цикл: `status=ok`, `prediction_mode=model`, свежая позиция, достаточный вход, тот же target и те же версии модели, плана и правил. Пропуск, ошибка, смена версии или fallback обнуляют счётчики последовательности; повторы одного `prediction_id` их не увеличивают. Для early существенное ухудшение — увеличение модуля опережения минимум на 60 с с тем же cooldown.

Равенство +120 или −60 не открывает ситуацию. Два признака одной цели не создают два независимых инцидента: ключ ситуации — `(run_id, tr_id, stop_visit_id)`, направление риска хранится в её истории. Если уверенно наблюдается противоположный риск, прежний эпизод архивируется с `risk_direction_changed`, начинается новый эпизод в той же ситуации.

### 8.3. Обновление, смена цели и архив

Повторные прогнозы одной цели добавляются в историю существующей ситуации. Материальное изменение увеличивает `attention_revision`: первое открытие, повторное открытие, существенное ухудшение, переход к недоступным данным. Обычный пересчёт не делает просмотренную ситуацию новой.

При потере данных активная ситуация сохраняется с новым качеством и исторической оценкой. Уменьшение риска не выводится из отсутствующего прогноза. Проблема данных создаёт отдельную запись на ТС с типом `telemetry_quality`, с дедупликацией повторов.

Запись `telemetry_quality` открывается при возрасте пригодной позиции более 180 с либо отсутствии такой позиции более 180 с после начала ожидаемого наблюдения ТС. Для live начало наблюдения задаёт включение ТС в активный парк запуска, для replay — начало его доступного исторического периода. Повторные циклы обновляют одну запись `(run_id, tr_id, issue_type)`. Закрытие — после двух последовательных свежих пригодных событий. Промежуточное состояние `limited` видно в сводке сразу, но не открывает отдельное предупреждение. Это правило не зависит от наличия целевого посещения или результата ML.

Когда онлайн-выбор переходит к следующему посещению, старая ситуация архивируется с причиной `target_changed`, а исход отмечается неизвестным, если факта нет. Связь с последующей ситуацией того же ТС сохраняется для навигации, но дельты между целями не считаются. Если новой цели нет и прогноз просрочен, ситуация архивируется как `forecast_expired`; это не `risk_reduced`. Сохранять старую карточку можно через личное наблюдение.

Если прежняя цель снова становится текущей после изменения плана, повторное открытие создаёт эпизод в той же ситуации с новой версией плана и ревизией. Изменение плана не переписывает старые прогнозы.

При получении оценки/факта прибытия исход дополняется и после архивирования, с источником и временем регистрации. Исход не подставляется в уже опубликованные входы ML. Удаление ситуаций оператором не предусмотрено.

### 8.4. Уведомления

В P0 достаточно уведомлений внутри приложения. Звук отключён по умолчанию и включается пользователем; звучит только для нового critical или его существенного ухудшения. Повторное подключение SSE не воспроизводит старые звуки. Для каждого пользователя дедупликация по ID уведомления и ревизии.

Система не принимает функции безопасности движения: SOS и аварийные сигналы терминалов не преобразуются в обычный рейтинг задержек. Их полноценная обработка требует отдельного согласованного контура.

## 9. Архитектура и взаимодействие компонентов

### 9.1. Схема

```text
NDTP-эмулятор / устройства
          │ TCP
          ▼
 telemetry-gateway ───────► Kafka ◄──────── csv-replay
                              │                  ▲
                              ▼                  │ файлы, виртуальные часы
                        processing-worker        │
                       /       │        \        │
          план, история       │ HTTP     кеш     │
                     /         ▼          \      │
       PostgreSQL + PostGIS   ml-service   Redis │
                 ▲             ▲             ▲   │
                 │        модель + ресурсы   │   │
                 │             ▲             │   │
                 │       offline-ml ◄────────────┘
                 │        │ отчёт, submission.csv
                 └──── backend ──────────────┘
                       │ REST + SSE
                       ▼
                 React frontend

Конфигурация, health-check, JSON-логи и метрики охватывают все сервисы.
Фактическая разметка доступна offline-ml, но не онлайн-плановому API.
```

### 9.2. Компоненты и границы

| Компонент | Ответственность | Вход → выход | Что ему не поручается |
|---|---|---|---|
| `data-import` | Проверка и версионирование файлов/справочников | CSV/конфигурация → план, связи, отчёт | Инференс и публикация факта как планового признака |
| `telemetry-gateway` | TCP, парсинг, единицы, идентификаторы | NDTP → нормализованное событие/ошибка Kafka | Модель и правила предупреждений |
| Kafka | Надёжный журнал после публикации | События → повторно читаемый поток | Источник истинного состояния UI |
| `processing-worker` | Дедупликация, состояние, сопоставление, срезы, ML-запросы, ситуации | Kafka + план + ML → БД, кеш, изменения | Модельная предобработка, самостоятельные пользовательские действия |
| `ml-service` | Версионируемая предобработка и инференс | Неизменяемый batch → прогнозы/ошибки | Чтение изменяемой БД платформы, отправка уведомлений |
| PostgreSQL/PostGIS | Долговременные данные, транзакции, геометрия | Справочники/события/результаты → восстановимое состояние | Автоматическое восстановление маршрутов без алгоритма |
| Redis | Последние позиции, окна истории, кеш проекций UI | Данные из надёжного хранилища → быстрые чтения | Единственная копия прогнозов/действий |
| `backend` | Права, чтение, действия, экспорт, SSE | REST/состояние БД → снимки и изменения | Прямой приём NDTP и отдельная трактовка риска |
| `frontend` | Представление и пользовательский сценарий | REST/SSE → рабочее место | Собственный расчёт задержки/правил риска |
| `offline-ml` | Признаки, обучение, оценка, submission | CSV/разметка → артефакт модели и отчёт | Запуск тяжёлого обучения в онлайн-запросе |
| `csv-replay` | Воспроизведение исторической доступности | CSV + часы → общий контракт событий | Обход worker и прямое наполнение UI |

Правила ситуаций и схемы данных оформляются общей библиотекой платформы, используемой worker и backend. Модельные признаки имеют другую общую библиотеку — для обучения и ML-сервиса. Это исключает две независимые реализации одной логики.

Базовый стек из исходной архитектуры: Python 3.12, asyncio, FastAPI/Pydantic, SQLAlchemy/Alembic, HTTPX, Kafka в KRaft, PostgreSQL/PostGIS, Redis; React/TypeScript/Vite, MapLibre GL JS и ECharts; Docker Compose. Версии зависимостей и образов фиксируются при реализации и проверяются совместным запуском. GPU используется только при обоснованной необходимости модели.

### 9.3. Один цикл обработки

1. Gateway связывает терминал с ТС, формирует ID и публикует событие с ключом ТС.
2. Worker проверяет схему и дубликаты. В одной транзакции сохраняет событие и долговременное текущее состояние; после commit подтверждает Kafka offset.
3. Worker обновляет Redis. Сбой кеша не отменяет сохранённое событие; кеш восстанавливается из БД.
4. Планировщик фиксирует согласованный срез и выбирает цели; сохраняет batch и его вход до отправки модели.
5. ML возвращает один результат на каждую цель. Worker валидирует ответ, сохраняет прогнозы, изменения ситуаций и записи доставки UI в одной транзакции.
6. Backend выдаёт снимок и последующие изменения только из зафиксированного состояния; frontend обновляет очередь, карту и открытую карточку.
7. Действие оператора проходит проверку роли/зоны, сохраняется транзакционно с аудитом и отражается в следующем обновлении.

### 9.4. Владение состоянием

P0: один worker владеет телеметрическим состоянием и единственным планировщиком запуска. Несколько backend-процессов допустимы: пользовательские операции защищены транзакциями и версиями записей. Два планировщика одной пары `(run_id, as_of)` не запускаются одновременно; уникальный ключ и блокировка в БД предотвращают повтор batch.

Обработка потока продолжается во время HTTP-инференса. Инференс имеет ограниченную конкурентность и очередь; бесконечный backlog прогнозов запрещён. При перегрузке пропускается устаревший цикл, сохраняются причина и метрика, а следующим выбирается актуальный срез.

## 10. Контракты событий и ML

### 10.1. Kafka

| Топик | Ключ | Содержимое |
|---|---|---|
| `telemetry.normalized.v1` | `run_id:tr_id` | Валидные по схеме нормализованные события, включая события с отсутствующей позицией |
| `telemetry.invalid.v1` | Доступный ID устройства/события | Ошибка разбора, привязки или схемы; причина, время, источник, ограниченный диагностический фрагмент |

Ошибки consumer также направляются в invalid-топик, если Kafka доступна; иначе сохраняются в структурированном локальном журнале с контролем размера. Секреты и неограниченные бинарные payload в логи не попадают.

Нормализованное событие:

| Поле | Тип / правило |
|---|---|
| `schema_version` | Строка `1`; несовместимые схемы не принимаются молча |
| `run_id`, `event_id` | Строки; уникальность события внутри запуска |
| `source` | Одно из `ndtp`, `replay`, `scenario` |
| `tr_id`, `unit_id` | Строки, связь проверена |
| `event_time`, `receive_time`, `ingested_at` | Время источника, получения и надёжного приёма платформой |
| `lat`, `lon`, `speed_kmh`, `heading_deg` | Конечное число или `null`; координаты валидируются парой |
| `location_valid` | Boolean; `true` не отменяет проверки диапазонов |
| `quality_flags` | Массив кодов: `invalid_position`, `missing_speed`, `late_event` и другие из версионируемого справочника |
| `source_identity` | ID пакета/сессии/сообщения, достаточные для повторной диагностики |

Gateway создаёт `event_id` один раз для принятого кадра и сохраняет его при повторах публикации в Kafka. Семантическая дедупликация NDTP использует устройство, время навигации и хеш payload, а не один NPH requestId, который может сбрасываться/переполняться. Для replay ID детерминирован из версии файла и номера строки; повтор того же запуска не создаёт новое событие. Новый `run_id` обозначает отдельный прогон и намеренно изолирован.

События одного ключа попадают в одну партицию. Это обеспечивает порядок доставки Kafka, но не сортировку по времени источника. Worker сам обрабатывает опоздание.

### 10.2. ML API

| Метод | Назначение |
|---|---|
| `GET /health/live` | Процесс работает |
| `GET /health/ready` | Модель и совместимые ресурсы загружены |
| `GET /v1/model-info` | Контракт модели, версии, необходимые входы и ограничения |
| `POST /v1/predict-batch` | Прогноз для согласованного набора целей |

`model-info` содержит: `model_version`, `feature_version`, поддерживаемые `schema_version`, длину истории, минимальное число наблюдений, допустимый возраст, обязательные поля, поддержку отсутствующего `cur_dev_s`, максимальный batch, потребность в соседних ТС/сети, правила разбиения batch, поддержку вероятностей/интервалов и перечень reason codes.

Состав запроса:

- `request_id`, `run_id`, `schema_version`, `as_of`, `schedule_version`, `network_version` (может быть `null`), `config_version`.
- `targets[]`: `prediction_id`, `tr_id`, `target_stop_id`, `target_time_begin`, `cur_dev_s`, его источник, время и качество.
- `telemetry[]`: события разрешённого среза с идентификаторами ТС, временем и признаками качества.
- `schedule_context[]`: плановые посещения, время, координаты, доступная последовательность. Фактические будущие времена отсутствуют.
- Контекст соседних ТС передаётся только при заявленной потребности модели; выбор соседей также фиксирован на `as_of`.

Состав ответа:

- `request_id`, `schema_version`, `model_version`, `feature_version`.
- `predictions[]`: `prediction_id`, `status=ok|insufficient_data|error`, `delay_s`, `error_code`, `reason_codes`, `quality_flags`.
- Опционально `late_probability`, `late_threshold_s`, `interval_lower_s`, `interval_upper_s`, `interval_coverage`; отсутствие выражается `null`.

Правила валидации:

1. Ровно один результат на каждый входной `prediction_id`, без лишних и повторяющихся ID. Пропавшая точка превращается в `error=missing_result`; валидные точки сохраняются. Дубликат делает соответствующую точку ошибочной, а не выбирается произвольно.
2. При `status=ok` значение `delay_s` обязательно и конечно; при остальных статусах — `null` с причиной.
3. Вероятность — число от 0 до 1 с явным порогом события. Интервал — упорядоченные границы и заявленный уровень покрытия. Не выводить вероятность из значения задержки по произвольной формуле.
4. Несовместимая схема/версия ресурса отклоняется до инференса. Ошибка формата — HTTP 422, несовместимость ресурса — 409, модель не готова — 503. Ответ содержит `error_code` и `request_id`.
5. Общие транспортные ошибки batch отделяются от ошибок конкретных целей. Успешные точки не теряются из-за соседней неуспешной точки.
6. Повтор запроса сохраняет ID и **тот же вход**. Входы одного ID с разными хешами отклоняются как конфликт. Платформа дедуплицирует сохранение результата независимо от наличия кеша в ML.
7. Модель может загружать неизменяемые ресурсы своей версии, но не читать текущее состояние Redis/PostgreSQL для дополнения запроса.

Бюджет цикла P0: до 5 с на формирование среза, до 20 с суммарно на HTTP/инференс/повторы, до 5 с на сохранение и публикацию. Начальный timeout отдельной попытки — 8 с, максимум одна повторная попытка в оставшемся бюджете для timeout/502/503/504. Ошибки схемы не повторяются. Значения корректируются нагрузочным тестом с сохранением общего 30-секундного бюджета либо официальным переходом на цикл 60 с.

Произвольное разбиение batch допустимо только если модель объявляет независимость целей. Для графовой модели границы контекста и батчей задаёт ML-команда. Если заявленные размеры не укладываются в бюджет, интеграция не считается принятой.

| `GET /health/live`, `GET /health/ready` | Техническое состояние backend |

Изменение настроек, привязок и импорт в P0 допускаются через административную CLI с аудитом и валидацией, без широкого публичного admin API. Запуск replay выполняется администратором через CLI/Compose; кнопки управления временем в операторском интерфейсе необязательны.

Начальный размер страницы — 50, максимум — 200. Временные выборки ограничены настраиваемым диапазоном, большие экспорты выполняются отдельной задачей. Действия имеют `Idempotency-Key`; повтор с тем же ключом и телом возвращает прежний результат, с другим телом — 409. Изменения проверяют ожидаемую ревизию, чтобы оператор не подтверждал незаметно более новое ухудшение.

### 11.2. REST + SSE

Сначала frontend получает REST-снимок с `event_cursor`, затем подписывается на события после этого курсора. Типы: `vehicle.updated`, `prediction.updated`, `incident.updated`, `data_quality.updated`, `notification.created`, `system.status`, `resync_required`. Конверт содержит уникальный `id`, `run_id`, `type`, `entity_id`, `entity_version`, время и полезные изменения.

Публикация строится через таблицу изменений/outbox, заполняемую в одной транзакции с бизнес-данными. Курсор отражает подтверждённый порядок публикации; нельзя использовать последовательный ID незавершённых транзакций как гарантию порядка commit. Издатель назначает порядок уже зафиксированным записям. Более поздно опубликованное старое состояние не заменяет новую `entity_version` в клиенте.

Backend хранит минимум 1 час доступных событий UI. Heartbeat — каждые 15 с; отсутствие heartbeat более 45 с переводит интерфейс в состояние разрыва соединения. После переподключения клиент всегда сверяет/обновляет REST-снимок; при недоступном курсоре сервер требует полную ресинхронизацию. Применение событий идемпотентно. События вне прав пользователя не передаются.

Redis Pub/Sub допустим как сигнал пробуждения backend, но не является единственным журналом. Ошибки браузерного соединения не влияют на сохранение прогнозов.

## 12. Модель хранения

### 12.1. Основные сущности PostgreSQL

| Сущность | Ключевые поля и связи |
|---|---|
| `runs`, `data_versions`, `config_versions` | Режим, часы, версии и происхождение каждого запуска |
| `users`, `zones`, `user_zones`, `zone_vehicles` | Учётные записи и серверная область доступа |
| `vehicles`, `device_bindings` | ТС; устройство, ТС и непересекающийся интервал действия связи |
| `schedule_versions`, `schedule_visits` | Версия, `stop_visit_id`, ТС, план, адрес, геометрия; уникальность `(schedule_version, stop_visit_id)` |
| `telemetry_events` | `run_id`, `event_id`, source identity, времена, измерения, качество; уникальность события |
| `vehicle_state` | Последние пакет/позиция/плановая связь; версия состояния и время обновления |
| `visit_observations` | Оценки/факты прибытия, источник, качество, исходные события, время регистрации |
| `prediction_batches`, `prediction_inputs` | ID batch, `as_of`, версии, зафиксированный вход либо неизменяемая ссылка и хеш |
| `predictions` | `prediction_id`, ТС, цель, batch, статус, mode, значение, качество и версия модели |
| `incidents`, `incident_episodes` | Уникальная ситуация `(run_id, tr_id, stop_visit_id)`, эпизоды открытия, состояния и причины |
| `data_issues` | Проблема данных `(run_id, tr_id, issue_type)`, начало, последнее изменение, состояние и история открытия/закрытия |
| `incident_events`, `incident_user_state` | Неизменяемый журнал; просмотренная ревизия и наблюдение пользователя |
| `feedback`, `audit_events` | Обратная связь; административные и пользовательские операции |
| `ui_outbox`, `ui_events` | Надёжная доставка изменений и срок хранения SSE-истории |

Связи: одно ТС имеет много посещений; посещение имеет много прогнозов разных моментов; прогноз связан с одним batch; ситуация объединяет прогнозы одной цели и содержит эпизоды и действия многих пользователей. Версия расписания хранится в прогнозе, чтобы изменение времени плана не меняло историческое значение задержки.

Фактическая разметка train/test хранится в отдельной схеме/артефактах с отдельными правами; онлайн-сервисам не предоставляется доступ к её таблицам. Оценка прибытия по текущей телеметрии хранится отдельно от конкурсного эталона.

Индексы обязательны по `(run_id, tr_id, event_time)`, целевым посещениям, `(run_id, as_of)`, lifecycle/зоне, а также пространственный индекс геометрий. Таблицы высокой частоты партиционируются по времени при необходимости выбранного профиля. План запросов и фактический объём проверяются нагрузочным тестом.

### 12.2. Согласованность

- PostgreSQL — источник долговременной истины. Redis содержит восстанавливаемые копии с версиями.
- Прогноз, изменения ситуации и outbox сохраняются атомарно. Пользовательское действие и его аудит — также атомарно.
- Kafka offset подтверждается после сохранения события и долговременного состояния. Повторная обработка после сбоя обновляет кеш из БД и не создаёт дубликат истории.
- При конкуренции применяется проверка версии записи/блокировка. Обновление backend не может стереть изменение worker.
- Точные входы прогнозов сохраняются независимо от TTL оперативной истории; хеш без самих данных недостаточен для повторного инференса.

### 12.3. Начальная политика хранения

| Данные | Срок / правило P0 |
|---|---|
| Kafka normalized | 72 часа |
| Invalid-события и диагностические payload | 7 суток, ограничение размера и доступа |
| Сырая нормализованная телеметрия в PostgreSQL | 30 суток |
| Прогнозы, входные срезы, ситуации, действия | 90 суток; входы допускается хранить сжатыми неизменяемыми файлами на защищённом volume со ссылкой/хешем |
| Версии плана, модели и правил | Не меньше срока связанных прогнозов |
| Redis | История модели + 10 мин; последние состояния восстанавливаемы; очистка завершённых run |
| SSE-журнал | Не менее 1 часа |
| Резервные копии | Ежедневно, хранение 7 последних успешных копий |

Сроки являются исходными настройками. Перед пилотом измерить объём на целевой нагрузке, выделить диск и проверить удаление/архивирование. Лимит диска не должен незаметно сокращать необходимое окно восстановления. Копируются не только таблицы, но и внешние файлы входов, конфигурация и артефакты модели, на которые они ссылаются.

## 13. Отказы и деградация

| Событие | Обязательная реакция | Проверяемый результат |
|---|---|---|
| Повтор Kafka-сообщения | Дедупликация по ID, восстановление проекции | Одно событие и один эффект в истории |
| Поздняя телеметрия | Сохранить, применить только к допустимым следующим срезам | Предыдущий прогноз неизменен, маркер не откатывается |
| Невалидная позиция | Сохранить связь/диагностику, оставить прежнюю пригодную координату | Не появляется достоверный маркер в нуле |
| Неизвестное устройство | Карантин, счётчик и причина | Нет фиктивного ТС и прогноза |
| Нет цели/конфликт расписания | Отсутствие прогноза с причиной | Нет цели вне +10–15 минут |
| ML timeout / 503 | Ограниченный повтор, затем fallback по условиям либо отсутствие | Worker принимает телеметрию дальше |
| Ошибка части ML batch | Сохранить корректные точки, ошибочные маркировать | Сбой одной цели не уничтожает остальные |
| Redis недоступен | Чтение из БД с лимитами, восстановление кеша | История и действия не теряются; интерфейс может замедлиться |
| PostgreSQL недоступен | Не подтверждать новые consumer offset, остановить сохранение прогнозов/действий, вернуть 503 | Нет ложного «сохранено»; после восстановления повтор из Kafka |
| Kafka недоступна | Ограниченная буферизация gateway, сигнал деградации | Нет бесконечной очереди; возможная потеря до Kafka учитывается явно |
| Перезапуск worker | Восстановить состояние и счётчики ситуаций из БД, продолжить offsets | Нет шквала повторных предупреждений |
| Старый ML-ответ пришёл после нового | Сохранить в историю, не заменить актуальный | UI не откатывается к меньшему `as_of` |
| SSE оборван / курсор устарел | Пометить разрыв, переподключиться, получить снимок | Клиент приходит к согласованному состоянию |
| Нет картографической подложки | Ошибка слоя, работа списка и карточки | Аналитический сценарий сохраняется |
| Перегрузка | Ограничить конкурентность, пропустить устаревший цикл с метрикой | Текущие прогнозы не ожидают неограниченную очередь |

При холодном старте сначала восстанавливаются состояние, справочники и модель; до readiness система не объявляется готовой. Неполная история после старта отражается как `insufficient_data`, а не маскируется фиктивным прогнозом.

## 14. Нефункциональные требования

### 14.1. Нагрузка и производительность

Следующие числа — **проектные цели приёмки**, ещё не достигнутые показатели. Стартовый профиль: 1 000 активных ТС, в среднем одно событие на ТС за 10 с (100 событий/с), всплеск до 300 событий/с в течение 60 с, до 10 одновременных операторских сессий. Инференс проверяется с 1 000 одновременно доступных целей, а не только при малом фактическом числе целей датасета.

Ориентир стенда: 8 vCPU, 32 ГБ RAM, SSD; фактические модель, размер диска, ОС, контейнерные лимиты и параметры запуска обязательно фиксируются в отчёте. Требование GPU не предполагается; если оно появляется, стенд и критерии пересогласуются до измерений.

| Показатель | Цель |
|---|---|
| Получение валидного сообщения → обновление UI | p95 ≤5 с при подключённом клиенте |
| Цикл срез → сохранённый прогноз | p95 ≤30 с для базового режима |
| Пропущенные циклы из-за перегрузки | <1% на часовом стабильном прогоне |
| REST-списки и карточки | p95 ≤1 с на указанном профиле |
| Подтверждение пользовательского действия | p95 ≤1 с без потери записи |
| Загрузка первого рабочего снимка | ≤3 с на локальной сети, без учёта внешних тайлов |
| Восстановление worker/Redis после рестарта | ≤5 мин на указанном профиле |

Процентили измеряются раздельно по стадиям. Для replay время вычислительных задержек измеряется реальными часами, возраст предметных данных — виртуальными. Ускоренный replay не используется как доказательство выполнения real-time SLO без отдельного измерения.

### 14.2. Надёжность и резервирование

Минимум — часовой непрерывный прогон под целевой нагрузкой и отдельные fault-тесты. Docker Compose с одной Kafka и одной БД не обеспечивает высокую доступность при потере узла; это допустимо для демонстрации/пилота, но не основание обещать промышленный SLA.

Для восстановления из ежедневной копии: проектный RPO ≤24 ч и RTO ≤60 мин на зафиксированном стенде. Проверяется реальным восстановлением в отдельное окружение. Восстановление отдельного worker из существующей БД/Kafka — другой сценарий с целью ≤5 мин.

### 14.3. Доступ и защита

- Для пилотного доступа по сети: HTTPS, серверная сессия в HttpOnly-cookie, защита изменяющих запросов от CSRF, ограничение частоты входа; пароли хешируются стандартной библиотекой. Собственная криптография не разрабатывается.
- Секреты поступают через окружение/секрет-хранилище и не попадают в репозиторий, примеры и логи. Демонстрационные пароли не используются вне локального режима.
- Kafka, Redis, PostgreSQL и ML API доступны только во внутренней сети; внешний TCP-приём ограничивается доверенными источниками. NDTP из поставленной спецификации не считается защищённым внешним интернет-каналом.
- Авторизация проверяется на каждом объекте/экспорте/SSE, включая прямой запрос ID чужой зоны.
- Длина комментариев, размеры CSV, HTTP body, TCP-буферов и batch ограничены конфигурацией. Ошибки не раскрывают stack trace клиенту.
- Аудит фиксирует пользователя/сервис, операцию, объект, время, результат и версию, но не пароль или полный session token.

### 14.4. Наблюдаемость — F14

Каждый сервис публикует live/ready и структурированные JSON-логи. Общие ID: `run_id`, `event_id`, `request_id`, `prediction_id`, `incident_id`.

Обязательные метрики: входной поток, активные устройства, ошибки CRC/схем/привязки, дубли и поздние события, Kafka lag, возраст позиций, размер очередей, batch duration p50/p95, ошибки/timeout ML, доля fallback/отсутствия прогноза, пропущенные циклы, задержка UI, число ситуаций по типу и качеству, состояние диска и БД.

Инженерные предупреждения: readiness упал; lag растёт более 60 с; три последовательных цикла ML завершились общей ошибкой; диск занят более чем на 80%; прекращена запись событий. Пороги хранятся в конфигурации. Они не смешиваются с операторской очередью транспортных рисков. Техническая панель — Prometheus/Grafana, а не замена рабочего интерфейса.

## 15. Развёртывание и комплектность

Поставка содержит Compose-конфигурацию, которая запускает `kafka`, `postgres` с PostGIS, `redis`, `telemetry-gateway`, `processing-worker`, `ml-service`, `backend`, `frontend`. Профили: `replay`, `ndtp-emulator`, `observability`, `offline-ml`. Публичная точка веб-приложения объединяет frontend/API; внутренний адрес ML не передаётся браузеру.

В репозитории должны быть:

1. Инструкция первого запуска на чистом окружении, требования к ресурсам и команды проверки.
2. `.env.example` без секретов; описание портов, временных зон, режима и всех значимых порогов.
3. Миграции БД, повторяемые импорты, подготовка начальной зоны и пользователя.
4. Зафиксированные зависимости/образы, артефакт модели либо проверяемая инструкция получения с контрольной суммой.
5. OpenAPI, схемы Kafka/ML, примеры запросов/ответов и описание кодов ошибок.
6. Команды обучения, оценки, submission, replay, резервного копирования и восстановления.
7. Набор сквозных сценариев, отчёт о качестве и отчёт нагрузочных/аварийных проверок.
8. Перечень известных ограничений и отличий от ТЗ; скрытые заглушки не допускаются.

Готовность компонентов задаётся health-check и зависимостями, а не фиксированными паузами запуска. Данные БД/Kafka и модель живут на устойчивых volumes. Очистка демонстрационного запуска производится явно по `run_id`, не удаляет другие данные.

Сервис-заглушка допустим для ранней интеграции с тем же API, но имеет `prediction_mode=stub` и явную плашку. Финальная приёмка прогнозной части требует обученной модели; stub не засчитывается как fallback или модельный результат.

## 16. Критерии приёмки

### 16.1. Главный демонстрационный сценарий

На фиксированной исторической выборке или явно помеченном сценарном наборе оператор:

1. Открывает зону, видит число доступных ТС, покрытие прогнозом и качество данных.
2. Получает значимое предупреждение, выбирает его в очереди и видит связанные ТС/плановую точку на карте.
3. В карточке отличает план, прогноз и наблюдение; находит время расчёта, свежесть, источник `cur_dev_s` и основания подсказки.
4. Отмечает просмотренную ревизию, ставит ситуацию на наблюдение и копирует сводку с целевым временем и ограничениями.
5. Получает следующий прогноз: та же цель обновляет историю, другая цель явно обозначена и не выдаётся за улучшение.
6. При искусственном обрыве телеметрии видит деградацию данных; ситуация не объявляется разрешённой.
7. После переподключения браузера видит актуальный согласованный снимок и сохранённое личное наблюдение.
8. Находит архивную историю с причиной завершения, не принимая её за доказательство предотвращённой задержки.

Исторический сценарий должен быть выбран после анализа доступных значимых отклонений. Если для демонстрации специально усилено опоздание, весь такой запуск маркируется `scenario` и исключается из отчёта ML.

### 16.2. Матрица обязательных проверок

| ID проверки | Требования | Дано / действие | Критерий успеха |
|---|---|---|---|
| A01 | F01 | Дважды импортировать один набор | Число сущностей не удваивается; версия и отчёт доступны |
| A02 | F01, F04 | Неизвестный timezone, конфликт устройства/ТС, повтор ID плана с разным временем | Импорт блокируется либо конфликт изолирован с конкретной причиной; нет молчаливой подмены |
| A03 | F02 | Handshake и default-пакет поставленного эмулятора | Устройство распознано, навигация проходит общий путь до UI |
| A04 | F02 | Разбитый кадр, несколько кадров, плохой CRC и неизвестная ячейка | Валидные кадры восстановлены; плохие изолированы; другие соединения работают |
| A05 | F02, F03 | Одно событие доставлено повторно и worker перезапущен между commit и offset | Одно сохранённое событие, один бизнес-эффект, кеш восстановлен |
| A06 | F03 | Свежий пакет с невалидной позицией | Возраст связи обновлён, возраст пригодной позиции продолжает расти, маркер не перемещён в ноль |
| A07 | F03, F05 | Позднее событие и поздний ответ старого batch | История сохранена; последняя позиция и прогноз не откатились |
| A08 | F04 | Посещения ровно T+10, T+15 и после T+15; несколько в окне | T+10 исключено, T+15 включено, выбрано первое допустимое; отсутствие/неоднозначность имеют явный статус |

### 16.3. Итоговая готовность

Первая версия принимается, когда все F01–F14 реализованы, A01–A28 имеют подтверждённый результат и команда передала комплект раздела 15. Раздельно фиксируются: техническая работоспособность платформы, качество модели и понятность операторского сценария. Успех одного направления не заменяет остальные.

Для проверки понятности провести сценарные задания с 3–5 действующими операторами при наличии доступа. До таких сессий выполнить внутреннюю проверку, а пользовательскую валидацию честно отметить как не проведённую. Критические ошибки интерпретации — принятие устаревшего прогноза за актуальный, гипотезы за факт, просмотра за выполненное вмешательство — должны быть исправлены до эксплуатационного пилота.

Завершение хакатонной поставки и допуск к реальной эксплуатации различаются: работа с реальными терминалами, подтверждение часового пояса/справочников и проверка с пользователями обязательны до соответствующего подключения, но не имитируются ради формального прохождения демонстрации.

Это порядок поставки возможностей, а не детальный план программирования. Оценки по дням добавляются после назначения исполнителей и подтверждения ограничений.

В небольшой команде роли совмещаются, но ответственность за интерфейсы остаётся явной.

## 19. Что сознательно отложено

P1 допускается после приёмки ядра и появления источников: полноценная маршрутная сеть, контроль интервалов на общей контрольной точке, группировка связанных ситуаций, модельные вероятности и интервалы, заметки/напоминания, контекст внешних действий и ресурсов.

P2 требует отдельного ТЗ: автоматическое регулирование движения, резерв и объезды, управление светофорами, причинная оценка эффекта, what-if, пассажирское приложение, долгосрочная управленческая аналитика и промышленная отказоустойчивая инфраструктура.

Flink/Spark, ClickHouse, Triton и GPU добавляются по измеренному ограничению, а не как самостоятельная цель. Назначение первой версии — достоверно пройти полный путь от входного события до понятного оператору прогноза и сохранённой истории.
