# Подробная документация системы прогнозирования задержек наземного транспорта

> Версия документа: 27.09.2026. Этот файл — самостоятельное описание работающего локального контура. Он объясняет, **что** делает каждый компонент, **как** данные проходят через систему и **как** проверить результат. Для пошаговой демонстрации жюри используйте [JURY_GUIDE.md](JURY_GUIDE.md), а для деталей обучения — [ml-models.md](development/ml-models.md).

## 1. Назначение

Система получает телеметрию наземного транспорта в формате NDTP, связывает её с плановым расписанием и прогнозирует отклонение от графика. Прогноз строится для первой плановой остановки, чьё время прибытия находится в интервале от 10 до 15 минут после момента прогноза.

Результат используется диспетчерским интерфейсом: оператор видит транспортные средства, актуальное состояние, прогноз задержки, качество данных и диагностическую информацию.

Важно разделять два режима работы:

- **live NDTP** — настоящий поток от выданного организаторами эмулятора; он проверяет протокол, приём, хранение и отображение в реальном времени;
- **historical replay** — воспроизведение исторических данных; это детерминированный способ проверить полный путь до ML-прогноза.

## 2. Что входит в поставку

```text
NDTP emulator / historical CSV replay
                |
                v
        telemetry gateway
                |
                v
          durable inbox (SQLite)
                |
                v
          processing worker
          |       |        |
          |       |        +--> data issues
          |       +-----------> vehicle state
          +-------------------> prediction targets
                                      |
                                      v
                              ML service (HTTP)
                                      |
                                      v
                         predictions / prediction cycles
                                      |
                                      v
                    REST API + SSE + dispatcher dashboard
```

Компоненты запускаются локально. Основной Docker Compose профиль поднимает `backend` и `ml-service`; при наличии образа NDTP дополнительно запускается `emulator`.

| Компонент | Роль | Вход | Выход |
|---|---|---|---|
| NDTP gateway | Принимает TCP-пакеты NDTP | TCP-соединения ТС | нормализованные telemetry events |
| Durable inbox | Надёжно принимает события до обработки | telemetry events | очередь необработанных событий |
| Processing worker | Обновляет состояние и готовит задачи прогноза | inbox и расписание | vehicle state, issues, targets |
| ML service | Выбирает модель и делает batch prediction | prediction targets | prediction и metadata routing |
| Backend API | Единая точка доступа | HTTP/внутренние события | REST, SSE, UI |
| Dashboard | Интерфейс диспетчера | REST/SSE | таблицы, карта, детали и история |

## 3. Основные понятия

- **`unit_id`** — физический идентификатор телематического терминала в NDTP. Его нужно зарегистрировать до начала live-потока.
- **`tr_id`** — идентификатор транспортного средства внутри системы. Он используется в расписании, состоянии и прогнозах.
- **Telemetry event** — одно нормализованное наблюдение: время, координаты, скорость, курс, GPS-validity и происхождение.
- **Schedule stop** — плановое прибытие ТС на остановку.
- **Prediction target** — срез данных, подготовленный worker для ML-сервиса в определённый момент времени.
- **Prediction cycle** — одна массовая попытка построить прогнозы. Она имеет статус, число обработанных целей и диагностические ошибки.
- **`run_id`** — логический идентификатор запуска. Он не позволяет смешать live-данные и результаты отдельного replay.

## 4. Приём NDTP-телеметрии

Backend поднимает отдельный TCP-сервер NDTP. Соединение начинается с handshake NDTP 6.2. После успешной идентификации сервер принимает realtime navigation packets.

На входе выполняются проверки:

1. структура и длина frame;
2. CRC16 Modbus;
3. порядок протокола: первым пакетом должен быть handshake;
4. соответствие identity терминала текущему соединению;
5. корректность полей навигации и флага GPS;
6. сборка fragmented TCP frames.

Некорректный пакет не должен останавливать сервер и не должен ломать другие соединения. Он фиксируется как data issue. Лимит одновременных соединений настраивается; в текущем профиле поддерживается до 1000 соединений.

### Почему `unit_id` регистрируется заранее

Эмулятор сообщает `unit_id`, а бизнес-система работает с `tr_id`. Регистрация связывает терминал с транспортным средством и предотвращает попадание неизвестного устройства в поток данных:

```http
PUT /api/v1/devices/{unit_id}
Authorization: Bearer <TRANSPORT_API_TOKEN>
Content-Type: application/json

{"tr_id":"demo-bus-1"}
```

В live-сценарии из `JURY_GUIDE.md` используется `unit_id=1166336` и `tr_id=demo-bus-1`.

## 5. Надёжный приём и хранение

После нормализации событие сначала сохраняется в persistent inbox SQLite, и лишь затем считается принятым. Такой порядок исключает потерю пакета между сетевым приёмом и worker.

SQLite настроен для локального надёжного контура:

- `WAL` для конкурентного чтения и записи;
- `synchronous=FULL`;
- включённые foreign keys;
- атомарные транзакции;
- индексы по ТС, времени и состоянию очереди.

Повторная доставка события безопасна. Для дедупликации используется семантический digest, не зависящий от технического времени приёма (`ingested_at`). Если одно и то же событие повторно пришло без смысловых изменений, новая запись не создаётся. Если один `event_id` несёт другое содержимое, это считается конфликтом и отображается как проблема данных, а не как тихая перезапись.

## 6. Worker: из события в состояние и задачу прогноза

Worker читает durable inbox и обрабатывает события последовательно в рамках своей транзакционной логики. Его ключевые обязанности:

1. отметить событие обработанным;
2. обновить последнее состояние ТС: позицию, скорость, курс, время и качество GPS;
3. сопоставить ТС с расписанием и ближайшими релевантными остановками;
4. вычислить доступные online-признаки;
5. сохранить data issues, если вход неполный или противоречивый;
6. сформировать prediction target для очередного prediction cycle.

Worker не вызывает ML на каждый пакет. Прогнозы запускаются пакетно через prediction cycle — так можно обрабатывать несколько ТС одним HTTP-запросом, ограничивать нагрузку и явно диагностировать ошибки конкретного цикла.

## 7. Расписание и временная привязка

Расписание загружается отдельно и содержит плановые прибытия. Для времени `T` система ищет первую остановку, которая попадает в окно:

```text
(T + 10 минут, T + 15 минут]
```

Целевая величина модели:

```text
target_delay_s = фактическое время прибытия − плановое время прибытия
```

Положительное значение означает опоздание, отрицательное — прибытие раньше графика. Если для ТС нет подходящей плановой остановки или недостаточно данных для target, worker не создаёт недостоверный прогноз: причина остаётся в диагностике цикла.

## 8. ML-сервис и выбор модели

ML вынесен в отдельный FastAPI-сервис. Backend передаёт в него пакет prediction targets через `POST /v1/predict-batch`; сервис возвращает результаты и сведения о выбранном режиме.

### 8.1. Режимы production router

| Режим | Когда применяется | Смысл |
|---|---|---|
| `COLD_STRICT` | Нет известного текущего отклонения `cur_dev_s` | cold-start Random Forest по расписанию, GPS и геометрии |
| `COLD_PLUS_DEV` | `cur_dev_s` корректно известен, но full-контекста недостаточно | cold-start RF с дополнительным признаком текущего отклонения |
| `FULL_CATBOOST` | Накоплена нужная история и известен `cur_dev_s` | основная CatBoost-модель полного контекста |

Критически важный нюанс текущего live-контура: worker пока не вычисляет `cur_dev_s`. Поэтому обычный end-to-end поток выбирает **`COLD_STRICT`**. Это не ошибка сервиса: router честно выбирает модель по фактически доступным признакам. `COLD_PLUS_DEV` и `FULL_CATBOOST` включаются только после передачи корректного текущего отклонения.

### 8.2. Признаки и качество

Offline feature matrix насчитывает 706 признаков: оконные характеристики телеметрии, контекст соседнего транспорта, log/signed-log преобразования, PCA и признаки расписания, GPS и физики движения.

Обучение использует purged blocked cross-validation: данные одного `tr_id` делятся по времени, а около validation-блока вырезается 45 минут. Это предотвращает утечку из 30-минутной истории признаков и 15-минутного горизонта прогноза. Synthetic-данные могут попасть только в обучение, но не в validation. Подробные метрики, артефакты и train-serving consistency находятся в [ml-models.md](development/ml-models.md).

## 9. Historical replay

Historical replay воспроизводит телеметрию из файлов и управляет виртуальным временем. Он нужен для повторяемой проверки всего контура:

```text
historical telemetry
  -> backend ingestion
  -> worker state and schedule matching
  -> prediction cycle
  -> ML batch
  -> SQLite
  -> dashboard/API
```

Именно этот сценарий подходит для демонстрации ML: данные, расписание и virtual clock согласованы, поэтому появляются prediction targets и результаты. Настоящий NDTP-эмулятор проверяет live ingestion, но сам по себе не гарантирует наличие полного исторического контекста для full-модели.

Готовый сценарий запуска, его параметры и ожидаемые результаты описаны в разделе «Сценарий B» файла [JURY_GUIDE.md](JURY_GUIDE.md).

## 10. REST API и SSE

Все защищённые запросы используют заголовок:

```http
Authorization: Bearer <TRANSPORT_API_TOKEN>
```

Ключевые endpoints backend:

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/health/live` | liveness backend |
| GET | `/api/v1/health/ready` | готовность backend и его зависимостей |
| PUT | `/api/v1/devices/{unit_id}` | регистрация терминала |
| POST | `/api/v1/telemetry` | HTTP ingestion нормализованной телеметрии |
| POST / GET | `/api/v1/schedules` | загрузка и просмотр расписания |
| GET | `/api/v1/vehicles` | список ТС |
| GET | `/api/v1/vehicles/{tr_id}` | состояние одного ТС |
| GET | `/api/v1/telemetry` | сохранённая телеметрия |
| GET | `/api/v1/dashboard` | данные диспетчерского экрана |
| POST / GET | `/api/v1/prediction-cycles` | запуск и просмотр циклов прогноза |
| GET | `/api/v1/predictions` | результаты прогнозирования |
| GET | `/api/v1/data-issues` | проблемы качества входных данных |
| PUT | `/api/v1/replay-clock` | управление virtual clock для replay |
| GET | `/api/v1/events` | SSE-поток обновлений |
| POST | `/api/v1/ml/check` | проверка связи с ML-сервисом |

ML-сервис публикует собственные endpoints: `/health/live`, `/health/ready`, `/v1/model-info`, `/v1/predict-batch`.

Swagger backend доступен на `http://127.0.0.1:8000/docs` после запуска.

## 11. Dashboard

Дашборд доступен на `http://127.0.0.1:8000/`. Он использует REST для первоначального состояния и SSE для обновлений. Интерфейс предназначен не для обучения модели, а для операционной проверки:

- сводка по транспорту и прогнозам;
- карта и текущее положение ТС;
- очередь внимания и incidents;
- карточка выбранного ТС;
- история и data quality;
- состояние prediction cycles.

Если на экране нет ожидаемого ТС, сначала проверьте `run_id`, регистрацию `unit_id`, фильтры интерфейса и endpoint `/api/v1/vehicles/{tr_id}`. Это позволяет отличить проблему UI от проблемы ingestion или schedule matching.

## 12. Запуск в Docker

### 12.1. Предварительные требования

Нужны Docker Engine/Docker Desktop, Docker Compose v2 и свободные порты `8000`, `8090`, `9201`, `18080`. Для настоящего NDTP-сценария дополнительно нужен архив организаторов `ndtp-telemetry-emulator.tar`, помещённый в `dataset/`.

Создайте `.env` в корне проекта:

```dotenv
TRANSPORT_API_TOKEN=jury-local-token-change-me-2026
TRANSPORT_ML_URL=http://ml-service:8090
```

Токен должен иметь длину не менее 16 символов. В Docker нельзя указывать `127.0.0.1:8090` в `TRANSPORT_ML_URL`: внутри контейнера backend этот адрес указывает на сам backend, а не на ML-контейнер. Используется DNS-имя `ml-service`.

### 12.2. Базовый запуск

```bash
docker compose --env-file .env -f infra/compose/compose.yaml up --build -d ml-service backend

curl http://127.0.0.1:8000/api/v1/health/live
curl http://127.0.0.1:8000/api/v1/health/ready
curl http://127.0.0.1:8090/health/ready
curl http://127.0.0.1:8090/v1/model-info
```

### 12.3. Live NDTP-демонстрация

1. Загрузите образ: `docker load -i dataset/ndtp-telemetry-emulator.tar`.
2. Запустите сервис `emulator` согласно [JURY_GUIDE.md](JURY_GUIDE.md).
3. Зарегистрируйте его `unit_id` через `PUT /api/v1/devices/{unit_id}`.
4. Включите поток через API эмулятора.
5. Откройте dashboard и/или запросите состояние ТС API.

Не сохраняйте выданный архив эмулятора в Git.

## 13. Диагностика: как искать проблему

Идите по потоку данных слева направо — это быстрее, чем сразу смотреть UI.

| Симптом | Что проверить | Вероятная причина |
|---|---|---|
| Backend не ready | `/api/v1/health/ready`, логи backend | backend не видит ML или не завершил инициализацию |
| ML не готов | `http://127.0.0.1:8090/health/ready` | не загружены checkpoints, ошибка контейнера или неверный URL |
| Нет ТС после live запуска | регистрация `unit_id`, логи emulator/gateway, `/vehicles/{tr_id}` | поток не включён, неверный unit_id или устройство не связано с tr_id |
| Есть телеметрия, нет прогноза | расписание, `prediction-cycles`, `data-issues`, окно 10–15 минут | нет подходящей остановки или недостаточно данных target |
| Режим не FULL_CATBOOST | metadata ответа ML и `cur_dev_s` | worker не передал текущую задержку; ожидаем `COLD_STRICT` |
| Порт занят | `docker compose ps`, процессы на порту | остался предыдущий запуск |
| Нужно начать заново | инструкции очистки БД в `JURY_GUIDE.md` | сохранённый SQLite state смешивает прогоны |

Для диагностического вызова ML можно использовать `POST /api/v1/ml/check`. Для событий и ошибок конкретного прогона всегда указывайте нужный `run_id` в запросах dashboard/predictions, если он предусмотрен endpoint.

## 14. Производительность и эксплуатационные свойства

Текущая реализация оптимизирована как надёжный локальный контур и конкурсная демонстрация:

- NDTP gateway изолирует ошибки соединения и умеет работать с фрагментированными пакетами;
- durable inbox отделяет сетевой приём от дальнейшей обработки;
- batch prediction снижает число запросов к модели;
- SQLite в WAL-режиме удобен для единой локальной поставки;
- REST/SSE дают UI актуальное состояние без периодического полного опроса.

Производственные целевые сервисы Kafka, PostgreSQL и Redis пока не являются частью текущего runtime. Документы, в которых они упомянуты как рабочие зависимости, описывают историческую или целевую архитектуру, а не обязательный способ запуска этой поставки.

## 15. Известные ограничения

Чтобы не создать завышенных ожиданий, текущая поставка сознательно **не заявляет**:

- распределённый production runtime на Kafka/PostgreSQL/Redis;
- автоматическое вычисление `cur_dev_s` live worker'ом;
- гарантированный переход live-потока на full-context CatBoost;
- хранение в Git архива NDTP-эмулятора организаторов;
- замену доменной проверки модели одной leaderboard-метрикой.

Для выбора модели ориентируются на leakage-safe CV и отдельный real holdout, а не только на внешний score. `COLD_STRICT` — нормальный и безопасный fallback, когда нужные признаки недоступны.

## 17. Рекомендуемый порядок знакомства

1. Прочитайте разделы 1–3 этого файла, чтобы понять назначение и термины.
2. Запустите базовый Docker-контур из раздела 12.
3. Выполните live NDTP-сценарий по [JURY_GUIDE.md](JURY_GUIDE.md), чтобы увидеть реальную телеметрию.
4. Выполните historical replay из того же guide, чтобы увидеть prediction pipeline.
5. Откройте dashboard, затем сопоставьте видимые результаты с `/dashboard`, `/vehicles`, `/predictions` и `/prediction-cycles`.
6. Если нужен ответ на вопрос о качестве, признаках или режиме модели — обратитесь к [ml-models.md](development/ml-models.md).

Такой порядок не смешивает проверку транспорта по протоколу с проверкой ML: сначала подтверждается ingestion, затем — воспроизводимый ML-контур.
