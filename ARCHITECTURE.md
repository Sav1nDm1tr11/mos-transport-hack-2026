# Архитектура системы прогнозирования задержек транспорта

Документ фиксирует предлагаемую архитектуру Near Real-Time и контракт интеграции с ML-модулем. Выбор, обучение и оценка модели находятся в ответственности ML-команды. Компоненты и API ниже — проектное решение, а не описание уже реализованной системы.

## 1. Назначение и ограничения

Система непрерывно принимает телеметрию, сопоставляет её с расписанием и каждые 30–60 секунд запрашивает прогноз отклонения. Диспетчер видит положение ТС, риск задержки, карточки инцидентов и рекомендации.

Для конкурсной задачи прогноз относится к конкретному плановому прибытию:

- момент расчёта — `T`;
- целевое посещение — первое с плановым временем в окне `(T + 10 минут, T + 15 минут]`;
- результат — `delay_s = фактическое время прибытия − плановое время прибытия`;
- положительное значение означает опоздание, отрицательное — опережение;
- для офлайн-точек целевое посещение уже задано в данных;
- если в онлайн-режиме подходящего посещения нет, прогноз для этого окна не формируется.

Окно 10–15 минут отсчитывается до **планового прибытия**. Оно не гарантирует такой же интервал до фактического возникновения инцидента.

При расчёте используются только доступные на момент `T` данные. В онлайн-режиме учитывается и момент поступления сообщения: поздняя телеметрия не должна задним числом изменять уже опубликованный прогноз.

## 2. Компоненты и стек

| Компонент | Стек | Ответственность |
|---|---|---|
| `telemetry-gateway` | Python 3.12, asyncio, confluent-kafka | Приём NDTP по TCP, разбор кадров, проверка пакетов, связь устройства с ТС, публикация нормализованных событий |
| Kafka | Apache Kafka, KRaft | Буферизация, журнал событий, повторное чтение после сбоя, независимые потребители |
| `processing-worker` | Python 3.12, confluent-kafka, Pydantic, HTTPX | Очистка и дедупликация, состояние ТС, история, сопоставление с расписанием, оркестрация инференса, сохранение результатов и расчёт алертов |
| `ml-service` | FastAPI, Uvicorn, библиотеки выбранной модели | Модельная предобработка, пакетный инференс, версия модели, прогнозы и признаки качества |
| PostgreSQL + PostGIS | PostgreSQL, PostGIS | Расписание, справочники, геометрия, история телеметрии, прогнозы, инциденты |
| Redis | Redis | Последние положения, ограниченные окна телеметрии, кеш актуальных прогнозов |
| `backend` | FastAPI, Pydantic, SQLAlchemy, Alembic | API интерфейса, фильтры, чтение состояния, действия диспетчера, доставка обновлений |
| `frontend` | React, TypeScript, Vite, MapLibre GL JS, Apache ECharts | Карта, индикация рисков, список инцидентов, карточки ТС и графики |
| `csv-replay` | Python | Воспроизведение исторической телеметрии через общий поток событий |
| Развёртывание | Docker Compose | Совместный запуск и конфигурация сервисов |
| Наблюдение | Prometheus, Grafana, структурированные JSON-логи | Доступность, скорость обработки, ошибки, свежесть данных |

Обработчик потока и оркестратор первоначально работают в одном контейнере `processing-worker`, но разделены на модули. Приёмник, Backend и ML-сервис запускаются отдельно.

Kafka сохраняется из исходной архитектуры. Роль стриминг-движка на первом этапе выполняет Python-worker. Flink/Spark, ClickHouse и Triton добавляются при подтверждённой необходимости по результатам измерений.

## 3. Поток данных

```text
NDTP-эмулятор / бортовые устройства
                 │ TCP
                 ▼
          telemetry-gateway
                 │ нормализованные события
                 ▼
               Kafka ◄──────── CSV Replay
                 │
                 ▼
         processing-worker ◄──── PostgreSQL/PostGIS
                 │                    план, справочники,
                 │                    геометрия
                 ▼
               Redis
      текущее состояние + история
                 │
                 ▼
      Оркестратор, каждые 30–60 с
                 │ HTTP: пакет данных на момент T
                 ▼
             ML-сервис
                 │ прогнозы
                 ▼
      Сохранение + правила алертов
                 │
       PostgreSQL + Redis
                 │
                 ▼
           Backend FastAPI
                 │ REST + SSE
                 ▼
          React-дашборд
```

1. Приёмник разбирает NDTP и публикует события в Kafka.
2. Worker сохраняет события, обновляет состояние ТС и историю, сопоставляет движение с планом.
3. Оркестратор каждые 30–60 секунд фиксирует момент `as_of` и собирает согласованный срез данных.
4. ML-сервис получает пакет целевых посещений и необходимый контекст через HTTP.
5. Worker сохраняет прогнозы, применяет правила риска и обновляет инциденты.
6. Backend отдаёт первоначальное состояние через REST и последующие изменения через SSE.
7. Действия диспетчера отправляются обычными HTTP-запросами.

Карта обновляет положение по мере обработки телеметрии. Пересчёт модели выполняется отдельно с заданным интервалом.

## 4. Приём и нормализация телеметрии

### 4.1. NDTP-приёмник

Приёмник отвечает за:

- TCP-соединения и handshake;
- сборку кадров: одно чтение TCP может содержать часть кадра или несколько кадров;
- проверку длины, типов ячеек и CRC согласно спецификации эмулятора;
- преобразование координат, знаков, времени и единиц измерения;
- обработку невалидных координат и повреждённых пакетов;
- сопоставление `unit_id` с `tr_id` через явный справочник;
- добавление времени получения и идентификатора события.

Неизвестное устройство не получает выдуманный `tr_id`: событие направляется в поток ошибок для разбора.

### 4.2. Kafka-топики

| Топик | Назначение | Ключ |
|---|---|---|
| `telemetry.normalized.v1` | Нормализованная телеметрия | `tr_id` |
| `telemetry.invalid.v1` | Необрабатываемые события и причина ошибки | Доступный ID устройства или события |

События одного ТС направляются в одну партицию. Порядок поступления не равен порядку `event_time`: worker отдельно обрабатывает запоздавшие сообщения.

Минимальные поля нормализованного события:

| Поле | Смысл |
|---|---|
| `schema_version` | Версия схемы события |
| `event_id` | Стабильный идентификатор для дедупликации повторной доставки |
| `source` | `ndtp` или `replay` |
| `tr_id`, `unit_id` | ТС и бортовое устройство |
| `event_time`, `receive_time` | Время события и получения |
| `lat`, `lon` | Координаты, допускается `null` |
| `speed_kmh`, `heading_deg` | Скорость и направление, допускается `null` |
| `location_valid` | Достоверность координат |
| `quality_flags` | Замечания к качеству события |

Идентификаторы передаются строками, чтобы избежать потери точности больших чисел в браузере.

## 5. Обработка состояния и расписания

`processing-worker` поддерживает последнюю позицию, историю движения, свежесть телеметрии и текущую связь ТС с плановыми посещениями.

Важные ограничения данных:

- `target_stop_id` соответствует `tt_action_item_id`, то есть плановому посещению, а не обязательно физической остановке;
- готовые ID маршрутов и дорожные полилинии нельзя предполагать доступными;
- PostGIS предоставляет геометрические операции, но алгоритм map matching реализуется отдельно;
- состояние дверей отсутствует в историческом `traffic.csv`; его нельзя делать обязательным входом модели без отдельного источника;
- в конкурсных точках `cur_dev_s` задан, а в потоке его нужно получать извне либо оценивать по уже обнаруженным посещениям остановок.

Для `cur_dev_s` хранятся источник и момент актуальности. Если оценка отсутствует, передаётся `null`, а не ноль.

Результат сопоставления должен содержать признаки качества. Низкая уверенность в определении участка или посещения передаётся в ML и интерфейс.

## 6. Граница ответственности с ML-командой

| Платформенная команда | ML-команда |
|---|---|
| Разбор NDTP и единицы измерения | Модельная нормализация и масштабирование |
| Связь устройства, ТС и плана | Формирование тензоров, эмбеддингов, графового входа |
| История до `as_of` и доступный пространственный контекст | Одинаковая предобработка при обучении и инференсе |
| Выбор целевого планового посещения | Прогноз и обработка недостаточного контекста |
| Доставка запроса, тайм-ауты, повторные попытки | Контракт поддерживаемых входов и версия модели |
| Хранение, алерты, рекомендации, UI | Величина отклонения и дополнительные выходы модели |

Модельная предобработка находится внутри ML-сервиса. Если отдельные признаки потребуется рассчитывать заранее в worker, ML-команда выделяет общий версионируемый пакет для обучения и онлайн-обработки.

ML-сервис получает вход через API и не читает изменяемые таблицы платформы самостоятельно во время запроса. Это делает момент прогноза воспроизводимым. Статическая геометрия или граф загружаются как версионируемые ресурсы.

## 7. API ML-сервиса

### 7.1. Методы

| Метод | Назначение |
|---|---|
| `POST /v1/predict-batch` | Пакетный прогноз |
| `GET /health/live` | Процесс работает |
| `GET /health/ready` | Модель и необходимые ресурсы загружены |
| `GET /v1/model-info` | Версии, длина истории, обязательные поля, возможности и ограничения |

`model-info` описывает требуемую историю, необходимость соседних ТС, правила разбиения пакетов, поддержку вероятностей и интервальных прогнозов.

### 7.2. Запрос

Ниже иллюстративный запрос с одной точкой истории. Реальный запрос содержит согласованное окно телеметрии и необходимый плановый контекст.

```json
{
  "request_id": "batch-00042",
  "run_id": "live",
  "schema_version": "1",
  "as_of": "2026-01-06T09:00:00Z",
  "schedule_version": "default",
  "network_version": "network-v1",
  "targets": [
    {
      "prediction_id": "vehicle-129964-target-53700336299-at-0900",
      "tr_id": "129964",
      "target_stop_id": "53700336299",
      "target_time_begin": "2026-01-06T09:12:00Z",
      "cur_dev_s": 45,
      "cur_dev_source": "stop_matching",
      "cur_dev_time": "2026-01-06T08:57:00Z"
    }
  ],
  "telemetry": [
    {
      "tr_id": "129964",
      "event_time": "2026-01-06T08:59:45Z",
      "receive_time": "2026-01-06T08:59:46Z",
      "lat": 55.75,
      "lon": 37.61,
      "speed_kmh": 18,
      "heading_deg": 90,
      "location_valid": true
    }
  ],
  "schedule_context": [
    {
      "schedule_version": "default",
      "tr_id": "129964",
      "stop_visit_id": "53700336299",
      "time_begin": "2026-01-06T09:12:00Z",
      "lat": 55.76,
      "lon": 37.62
    }
  ]
}
```

`network_version` может быть `null`, если модель не использует статическую сеть. Несовместимая версия ресурса должна приводить к явной ошибке, а не молчаливой подмене контекста.

### 7.3. Ответ

Значения ниже иллюстративные и не являются результатами измерений.

```json
{
  "request_id": "batch-00042",
  "schema_version": "1",
  "model_version": "model-v3",
  "predictions": [
    {
      "prediction_id": "vehicle-129964-target-53700336299-at-0900",
      "status": "ok",
      "delay_s": 180,
      "late_probability": 0.82,
      "late_threshold_s": 120,
      "reason_codes": ["LOW_SPEED_RECENT"],
      "quality_flags": []
    }
  ]
}
```

Правила контракта:

- один результат на каждый `prediction_id`;
- `delay_s` — конечное число в секундах со знаком при `status = ok`;
- возможные статусы точки: `ok`, `insufficient_data`, `error`;
- при ошибке точки `delay_s = null`, дополнительно возвращается `error_code`;
- ошибка одной точки не отменяет успешные результаты остальных;
- вероятность, объяснения и прогнозные интервалы — дополнительные возможности модели;
- если вероятность не поддерживается, возвращается `null`; её нельзя вычислять произвольно из точечного прогноза;
- для вероятности явно указывается событие: например, `delay_s > late_threshold_s`;
- неизвестная схема и невалидный запрос отклоняются до инференса;
- все временные поля API содержат часовой пояс; внутри системы используется UTC;
- часовой пояс исходных CSV определяется явно до преобразования;
- повторная отправка одного логического запроса сохраняет его идентификаторы и входной срез.

### 7.4. Договорённости перед интеграцией

ML-команда и платформенная команда фиксируют:

1. Длину истории и допустимую частоту наблюдений.
2. Необходимость соседних ТС и способ выбора пространственного контекста.
3. Можно ли делить сеть на независимые пакеты; для GNN произвольное разбиение недопустимо без проверки.
4. Допустимые пропуски и минимальный объём данных.
5. Окончательный состав `schedule_context` и статических ресурсов.
6. Максимальный размер пакета и бюджет времени инференса, укладывающийся в цикл обновления.
7. Версию схемы, правила совместимости и способ доставки артефактов модели.

Поставка ML-команды: Docker-образ, модель с предобработкой, описание API, пример запроса и ожидаемого ответа. Пока модель не готова, сервис-заглушка реализует тот же контракт и возвращает `cur_dev_s` с обозначением резервного режима.


### 7.5. Текущая реализация model routing

Локальный профиль реализует один внешний ML API, внутри которого выбирается модель по доступному контексту:

```text
PredictionBatch
      |
      +-- full CatBoost загружен + cur_dev_s известен + истории достаточно
      |       -> FULL_CATBOOST
      |
      +-- cur_dev_s известен
      |       -> COLD_PLUS_DEV
      |
      +-- иначе
              -> COLD_STRICT
```

Cold-start модели -- Random Forest на snapshot, schedule и физических признаках. Full CatBoost использует накопленную телеметрию и расширенные rolling/spatial признаки. Конкретная модель не является частью контракта backend: каждый результат возвращает `model_version`, `feature_version` и reason code выбранного режима.

Full CatBoost optional. Если checkpoint отсутствует или не загрузился, сервис остается работоспособным на cold-start RF. Порог перехода на full-модель задается параметрами истории сервиса.

Текущий full feature builder восстанавливает только признаки, доступные из `PredictionBatch`. Offline-only поля и PCA без сохраненного fitted preprocessing остаются missing; поэтому перед production-фиксацией full-модели требуется отдельная train-serving проверка или переобучение на полностью online-reconstructable признаках.

## 8. Хранение данных

### PostgreSQL — долговременное состояние

| Сущность | Содержимое |
|---|---|
| `vehicles`, `device_bindings` | ТС и соответствия бортовым устройствам |
| `schedule_visits` | Плановые посещения, время, геометрия и связь с ТС |
| `telemetry_events` | Нормализованные события с уникальным `event_id` |
| `prediction_batches`, `predictions` | Запросы, момент среза, версия модели, прогнозы, статусы |
| `incidents` | Текущий статус инцидента, риск, связанное посещение |
| `incident_events` | История изменения статусов и действий диспетчера |

Фактические времена из обучающей раздачи не включаются в доступный онлайн-сервисам плановый контекст. Офлайн-разметка хранится и обрабатывается отдельно.

### Redis — восстанавливаемое оперативное состояние

- последние позиции и свежесть телеметрии;
- ограниченная история, необходимая модели;
- последние актуальные прогнозы;
- кеш подготовленных для UI данных.

PostgreSQL является источником долговременной истины. Redis восстанавливается из сохранённых данных и журнала событий. Периоды хранения Kafka, PostgreSQL и окон Redis задаются явно и согласуются с необходимой глубиной восстановления.

Сначала прогноз сохраняется в PostgreSQL, затем обновляется кеш. Уникальные ключи защищают от дублей. Старый ответ модели не заменяет более новый актуальный прогноз: сравнивается `as_of`, а не время завершения HTTP-запроса.

## 9. Backend и диспетчерский интерфейс

Предлагаемый внешний API:

| Метод | Назначение |
|---|---|
| `GET /api/v1/vehicles` | ТС, положения, свежесть, актуальные риски |
| `GET /api/v1/vehicles/{tr_id}` | Карточка ТС |
| `GET /api/v1/incidents` | Инциденты с фильтрами |
| `GET /api/v1/predictions` | История прогнозов |
| `POST /api/v1/incidents/{id}/acknowledge` | Подтверждение диспетчером |
| `GET /api/v1/events` | SSE-поток обновлений |

Backend определяет пороги риска, объединение повторных предупреждений, переходы статусов и рекомендации. Чтобы worker и API одинаково трактовали инциденты, правила оформляются общим модулем платформы. Worker применяет их при обработке прогнозов, API — при действиях диспетчера.

Карточка инцидента показывает:

- ТС, целевое посещение и место;
- время расчёта и планового прибытия;
- прогноз отклонения и вероятность, если она доступна;
- наблюдаемый паттерн и качество данных;
- возраст телеметрии;
- рекомендацию и статус подтверждения.

Потеря связи отображается отдельным состоянием и не считается низким риском. Объяснения отражают наблюдаемые паттерны: без соответствующего источника нельзя утверждать, что причина — ДТП или длительная посадка.

Первоначальный снимок приходит через REST, обновления — через SSE. После переподключения клиент повторно получает актуальный снимок. В первой версии Backend может опрашивать хранилище и отправлять изменения. Redis Pub/Sub допускается как ускоряющий сигнал, но не как единственный источник обновлений.

Grafana используется для технического наблюдения. Основное рабочее место диспетчера — специализированный React-интерфейс. Для карты отдельно конфигурируется источник подложки; наличие MapLibre не предоставляет картографические тайлы автоматически.

## 10. Надёжность

- **Повторная доставка:** обработка допускает повторы; уникальные `event_id` и `prediction_id` предотвращают дубли.
- **Подтверждение Kafka:** offset фиксируется после надёжного сохранения события. При восстановлении повторная обработка безопасна.
- **Обрыв телеметрии:** сохраняется последнее состояние, растёт возраст данных, новые прогнозы маркируются как ограниченные либо прекращаются.
- **Отказ ML:** ограниченные повторные попытки и тайм-аут; при длительном отказе — резервный прогноз при достаточно свежем `cur_dev_s`, иначе статус отсутствия прогноза.
- **Перегрузка:** bounded-очереди и ограничение одновременных запросов; для отображения приоритет у актуальных срезов, пропуски циклов учитываются в метриках.
- **Запоздавшие события:** могут участвовать в следующем срезе, но не переписывают историю ранее опубликованных прогнозов.
- **Redis недоступен:** состояние восстанавливается из долговременного хранилища; кеш не является единственной копией.
- **SSE прерван:** клиент переподключается и обновляет снимок.
- **Повреждённый пакет:** фиксируется ошибка, остальные устройства продолжают обрабатываться.

Для источника задаётся политика подтверждения и буферизации согласно протоколу. Нельзя заявлять отсутствие потерь только на основании использования Kafka: отказ приёмника до публикации также должен учитываться.

## 11. Развёртывание и наблюдение

Docker Compose запускает:

- `kafka`;
- `postgres` с PostGIS;
- `redis`;
- `telemetry-gateway`;
- `processing-worker`;
- `ml-service`;
- `backend`;
- `frontend`.

Дополнительные профили: `csv-replay`, NDTP-эмулятор, Prometheus и Grafana. Kafka в одном экземпляре подходит для демонстрации, но не обеспечивает отказоустойчивость к потере узла.

Веса модели монтируются или поставляются внутри ML-образа. GPU предоставляется только ML-контейнеру, если требуется выбранной модели. Обучение выполняется отдельным процессом и не блокирует инференс.

Базы, Kafka и ML API доступны во внутренней сети контейнеров. Наружу публикуются необходимые интерфейсы: веб-приложение, Backend и TCP-приёмник. Настройки и секреты передаются через окружение, образы и зависимости фиксируются по версиям.

Основные метрики:

- скорость входного потока и число активных устройств;
- consumer lag Kafka;
- доля невалидных событий и дублей;
- возраст последней телеметрии;
- длительность подготовки пакета и инференса, p50/p95;
- время от получения сообщения до обновления интерфейса;
- число ошибок, резервных прогнозов и пропущенных циклов;
- количество активных алертов.

Конкретные SLO фиксируются после измерений. До этого техническое требование — весь цикл подготовки и инференса должен укладываться в выбранные 30–60 секунд при согласованной нагрузке.

Документация API формируется через OpenAPI/Swagger, документация модулей — через Sphinx. Логи связываются идентификаторами `event_id`, `request_id`, `prediction_id`.

## 12. Проверка интеграции

1. Сервис-заглушка позволяет собрать весь путь до дашборда без готовой модели.
2. CSV Replay публикует данные в общий топик и использует управляемые часы воспроизведения.
3. NDTP-эмулятор проверяет протокол, переподключения и обработку пакетов. Его случайное движение не считается воспроизведением реального расписания.
4. На одинаковом историческом срезе проверяется совпадение офлайн- и онлайн-предобработки.
5. Проверяются дубли, поздние события, недостаточная история, частичная ошибка пакета и отсутствие целевого посещения.
6. Проверяются отказ ML, перезапуск worker, восстановление Redis и переподключение интерфейса.
7. Перед подключением новой модели выполняется проверка совместимости API и статических ресурсов.

## 13. Расширение архитектуры

| Расширение | Основание для добавления |
|---|---|
| Flink или Spark Structured Streaming | Подтверждённая необходимость распределённой обработки и сложного состояния |
| ClickHouse | Объём истории и аналитические запросы превышают практические возможности выбранной конфигурации PostgreSQL |
| Triton / ONNX / TensorRT | Измеренный bottleneck инференса и совместимость выбранной модели |
| Отдельные очереди запросов и результатов ML | Потребность в независимом масштабировании и асинхронном выполнении |
| Несколько processing-worker | Разделение нагрузки по партициям с согласованным владением состоянием и планированием запросов |
| What-if | Наличие отдельной модели последствий управленческих действий |
